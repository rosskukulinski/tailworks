# D1 databases

tailworks runs Cloudflare D1 code unchanged: declare `d1_databases` in
`wrangler.jsonc` and use `env.DB` as on Cloudflare. Each database is a
SQLite database that belongs to your workload, served on the host that
runs it, with every write kept in mgmt so the database survives a host
restart, the loss of a host and a move to another host. Design:
[ADR-038](design/adr/038-d1-databases.md). What matches Cloudflare and what doesn't:
[COMPAT.md](COMPAT.md#d1).

## Bind a database

```jsonc
// wrangler.jsonc
{
  "name": "notes",
  "main": "src/index.js",
  "compatibility_date": "2026-04-01",
  "d1_databases": [
    {
      "binding": "DB",
      "database_name": "notes-db",      // the database's name in tw
      "database_id": "…",               // wrangler's; tw ignores it
      "migrations_dir": "migrations",   // default
      "migrations_table": "d1_migrations" // default
    }
  ]
}
```

```js
export default {
  async fetch(req, env) {
    await env.DB.prepare("INSERT INTO notes (body) VALUES (?)").bind("hello").run();
    const { results } = await env.DB.prepare("SELECT id, body FROM notes").all();
    return Response.json(results);
  },
};
```

The whole API works, in the Worker and in Durable Objects:
`prepare().bind()` with `first()` / `first(column)` / `all()` / `run()` /
`raw({ columnNames })`, `batch()` (atomic), `exec()`, and `withSession()`.
`dump()` throws; use `tw d1 export`.

A database belongs to the workload that binds it (and its replicas). Its
name is `database_name`; two workloads that use the same name get two
databases. To share data, call the owning workload over the tailnet.

## Migrations

Migrations are wrangler's: numbered `.sql` files in `migrations_dir`,
applied in name order and recorded in `migrations_table`. An existing
wrangler project's migrations apply as they are.

```sh
tw d1 migrations create notes-db "create notes"   # migrations/0001_create_notes.sql
$EDITOR migrations/0001_create_notes.sql
tw deploy
tw d1 migrations list notes-db                    # what isn't applied yet
tw d1 migrations apply notes-db
```

Each migration runs as one batch with its record, so it is applied whole
or not at all. Migrations are not applied by `tw deploy`; run `apply`
when you want the schema change. `<db>` is the `database_name` or the
binding name. The commands read `./wrangler.jsonc`, so run them in the app
directory (or pass `--workload`).

Migrations only move forward. `tw rollback` redeploys older code but
leaves the database as it is, with every migration that was applied still
applied (as on Cloudflare). Write migrations that the previous version of
the code can still run against (add columns and tables before you use
them, drop them a release later), or roll the schema back yourself with a
new migration.

A preview (`tw deploy --preview`) is a workload of its own,
`<workload>--preview-<alias>`, so its databases are its own and start
empty. Apply migrations to it with `--workload <workload>--preview-<alias>`.
`tw promote` deploys the preview's code to the workload and doesn't copy
its data: apply the new migrations to the workload's databases before you
promote.

## `tw dev`

`tw dev` has D1. Its databases are in memory for that run: each start
(and each reload) applies the pending migrations first, so the app sees
its schema on the first request.

## Operator commands

| Command | |
|---|---|
| `tw d1 create <db>` | create an empty database (a first write creates it too) |
| `tw d1 list` | the workload's databases |
| `tw d1 execute <db> --command "<sql>"` | run SQL as one batch, print the rows (`--json` for D1's results) |
| `tw d1 execute <db> --file schema.sql` | the same from a file |
| `tw d1 export <db> --output backup.sql` | the schema and rows as SQL, like `wrangler d1 export` |
| `tw d1 delete <db>` | delete the database and its data; there is no undo, so it asks you to type the name (`--yes` skips the prompt) |

They take `--workload <name>` (default: the app in the current directory)
and `--tenant`, and work from a `tw link`ed machine. `execute`, `export`
and migrations reach the database through the running workload, so deploy
first. A write is audited (`d1_write`, the statement count only, never the
SQL).

## How it works

Each database is a SQLite Durable Object owned by the platform (tenant
code can't reach it except through the binding). Reads run locally. A
write is first tried in a transaction that is rolled back, then appended
to mgmt's journal for the database (sealed at rest, accepted only from the
host holding the workload's lease), then applied, so an acknowledged write
is never only on one host's disk. A host that starts the workload without
the database (after a move, or a lost disk) rebuilds it from the journal.

Consequences worth knowing:

- Every write waits for mgmt. If mgmt is unreachable, writes fail with
  `[store_unavailable]`; reads keep answering from the host's copy.
- When a host rebuilds a database from the journal, non-deterministic SQL
  runs again: `random()`, `randomblob()`, `datetime('now')`, `DEFAULT
  CURRENT_TIMESTAMP`. Bind such values from JS where they must not
  change.
- A write that fails when the journal is replayed (only non-deterministic
  SQL can: say, a `random()` key that now collides with a row) is never
  skipped: the database stops there and is degraded. See
  [Recovery](#recovery).
- A bound JS number is stored as a REAL unless the column has INTEGER
  affinity (as under `wrangler dev`). It reads back as the same number.
- The journal keeps every write (up to 1 GiB per database); there is no
  compaction yet.

## Recovery

If a host can't apply a journal entry while it rebuilds or catches up a
database, it stops before that entry rather than skip it (a skipped write
would leave a database that differs from the one whose writes were
acknowledged, and later writes could depend on it). The database is then
degraded:

- reads answer from what was applied before the failing entry;
- writes fail with `D1_ERROR: [store_degraded] …`, naming the entry and
  SQLite's error (`tw d1 execute` fails with `409 store_degraded`);
- each later sync tries the entry again, and the database heals if it
  applies.

An entry written by a newer tailworks needs a tw-hostd upgrade. For an
entry that will never apply, rebuild the database from what applied:

```sh
tw d1 export notes-db --output backup.sql   # first line: the failing entry and its error
tw d1 delete notes-db --yes
tw d1 create notes-db
tw d1 execute notes-db --file backup.sql
```

The export leaves out the failing entry and every write after it; re-run
any of those you still want.

## Limits

| | |
|---|---|
| SQL statement | 100 KB |
| Bound parameters | 100 per statement |
| A string or BLOB | 2 MB |
| Statements per request | 1000 |
| One write (statement or batch), encoded | 2 MiB |
| Result of one request | 16 MiB |
| Database | 1 GiB |
| `tw d1 export` | 16 MiB |

A request over a limit fails with `D1_ERROR: …` before SQLite runs it (or,
for the result, before it is sent), and nothing of it is applied.
