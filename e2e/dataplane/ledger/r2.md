# Data-plane loop ledger: R2

Issue #420 (a follow-up to #415). Process: `../LOOP.md`. Findings are filed
as GitHub issues labelled `dataplane-chaos`.

## The rig

`TestR2` (`r2_test.go`) runs the cluster of `TestDataplane` (mgmt on
SQLite, three hosts, each through its own cuttable proxy to mgmt) with
`testdata/r2`, a workload that does every R2 operation on one bucket.

- **Backends.** `fs`: each host's own directory. `s3`: one Garage
  container (`dxflrs/garage:v2.1.0`; MinIO no longer publishes images)
  started with `chaoskit.Run`, which every host reaches through a
  `chaoskit.Proxy` of its own, so one host's path to it can be cut
  (blackhole or reset) or slowed. Only the container the run started is
  removed, by ID. `e2e/chaoskit` is shared with `e2e/multimgmt` (its
  Postgres fault proxy).
- **Clients** (`r2client_test.go`): four register clients on `k0`–`k3`
  (put 40%, get 35%, head 10%, delete 10%, list 5%; 1 put in 10 sends its
  MD5, 1 in 20 a wrong one), a multipart client on `m0`/`m1` (create, a
  5 MiB part and a small one, a wait of up to 20 s, then complete, or
  abort 1 time in 5), a reader of the multipart keys, and probes (get,
  put, delete) of endpoints that are no longer current. A value's bytes
  are `<op ID>|` repeated (multipart: `<op ID>#<n>|` per part), so every
  read names the write it saw and every byte and etag is checked.
- **At quiescence:** after healing, a head and a get of every key and a
  list, from every current endpoint (both replicas), and a count of the
  blobs in the backend.

## Scenarios (`nemesis_test.go`)

| Scenario | Workload | Backend | Faults |
|---|---|---|---|
| `r2-fs` | one fenced copy (a DO class) | fs | kill-host, crash-hostd, kill-mid-put, cut-short, cut-takeover, pause-takeover, move, restart-mgmt |
| `r2-s3` | one fenced copy | s3 | the same, plus cut-s3, slow-s3 |
| `r2-replicas` | `"replicas": 2`, no DO class (no fence) | s3 | kill-host, crash-hostd, kill-workerd, kill-mid-put, cut-short, cut-s3, slow-s3, restart-mgmt; faults alternate between the two replicas' hosts |

New faults: `cut-s3` (one host's path to S3: blackhole or reset, 3–20 s),
`slow-s3` (100 ms–1 s per read, 5–20 s), `kill-mid-put` (a 1–4 MiB put,
then SIGKILL of the host 0–600 ms later: during the blob write, between
it and the journal append, or during the append).

The blob is written before the journal append (`store-r2.js` `#put`), so
"SIGKILL between the journal write and the blob write" has one order;
`kill-mid-put` and `kill-host` under load cover it and the windows around it.

## Invariants (`check_r2_test.go`)

| ID | Invariant |
|---|---|
| R1 | Each key is a register (unique values): no read of a value never written to it, or written after the read ended; none of a value an acknowledged write had replaced before the read began; none older than what an earlier read saw. A write with no answer may land any time after it was sent. Reads from a host inside a declared mgmt outage (its cut-off, or mgmt down) + 8 s are R4's |
| R2 | Bytes and etags always match (`<md5>`, `<md5 of md5s>-2`); a put with a wrong MD5 is never acknowledged or read. At quiescence: s3: every key the index has reads back; fs: the index (head) still has it, and get returns it or fails with exactly `r2_blob_missing` when its bytes were written on another host. On s3, `r2_blob_missing` outside an outage fails |
| R3 | No write (put, delete, multipart) acknowledged while its host is cut off from mgmt, or while mgmt is down (SIGKILL restarts), or by a host the lease has moved away from |
| R4 | Stale reads only inside a declared outage; for a fenced workload not past 40 s into a host's cut-off (FenceAfter 30 s + a heartbeat + slack); no answer at all from a fenced host cut off for longer. Reported: stale reads and `r2_blob_missing` from a stale index inside outages, reads over 3 s during one |
| R5 | At quiescence `list` = the keys head finds; every one of them reads back (R2). Reported: blobs in the backend vs referenced by the index (orphans from crashes, unfinished uploads) |
| R6 | A multipart object is read whole (both parts of the same upload) or not at all; an upload created and never aborted is not lost (`noSuchUpload` outside an outage fails) |
| R-conv | After healing, every copy serves within 60 s |

`TestR2Checkers` (`check_r2_unit_test.go`) runs the checkers on small
made-up histories, without a cluster.

## Findings

| ID | Verdict | Invariant | Issue | Summary |
|---|---|---|---|---|
| F-R2-1 | FIXED (#573) | R1, R3 | #562 | A store write that changes nothing on the local copy (R2/KV delete of an absent key, failed `onlyIf`, D1 `UPDATE` matching nothing) is acknowledged without asking the journal (`store.js` `commit()`: `if (!es.length) return this.seq`). A replica behind the other one acknowledged a delete of a key just put there, and the key stayed (1.5 s after the last fault). Hosts cut off from mgmt acknowledged 16 (replicas) and 8 (fs, mgmt down) deletes. Regression test `hostd:TestStoreNoopWriteChecksJournal` |
| F-R2-2 | FIXED (#576) | R2, R5 | #574 | H1 below. A put (or part) whose journal append commits but whose answer is lost deletes its blob (`store-r2.js` `#put`/`#uploadPart` catch), though the index has the row: the key reads `r2_blob_missing` until overwritten. Not hit by chance yet in the loop (needs a lost answer after the commit); reproduced with fakemgmt `LoseAppendAnswers`. Regression test `hostd:TestR2PutLostAnswer` |

## Hypotheses and notes

| ID | Status | Note |
|---|---|---|
| N1 | Documented | With replicas on s3, a replica whose index copy is stale during an outage can name a blob the other replica has since replaced and garbage-collected: the read fails `r2_blob_missing` (137 in r2-replicas seed 1, all inside the cut-off host's outage). Not wrong bytes; docs/r2.md now says so. R4 counts them |
| H1 | CONFIRMED → F-R2-2 | A put whose journal append commits at mgmt but whose answer is lost (mgmt killed or cut mid-append) is answered as a failure, and `#put` then deletes its blob: the index names a missing blob | Reproduced deterministically (`TestR2PutLostAnswer`). The loop's `restart-mgmt` (SIGKILL) and `cut-short` under load can hit it, but the window is a few ms per append; a mgmt-side delay fault would widen it (the mgmt proxy can only cut) |
| N2 | Filed #580 (needs a decision) | fs: the garbage collector deletes through the host the workload runs on now, so after a move the old objects' blobs stay on the old host's disk for good. `r2-fs` seed 2 (two takeovers) ended with 1047 blobs and 10 referenced |
| H2 | OPEN | Garage behind a reset or blackholed proxy: an S3 PUT that the backend stored but whose answer was lost leaves an orphan blob only (the index write never starts) | Orphans are reported by R5 (2–27 per run, most from crashes and unfinished uploads). No harm seen |
