# Notes for coding agents

The design is in `docs/design/`: the RFC (`RFC.md`) and one file per ADR
(`adr/`). This repo is public. Don't add internal figures (pricing,
Tailscale-internal limits, roadmap or tooling) to any file here.

Several agents work in this repo at once, each on its own branch or
worktree. Most merge pain has come from everyone editing the same few lines,
not from real logic clashes. These rules keep parallel branches out of each
other's way. They come from replaying the last 11 conflicted merges
(2026-11-14).

## Parallel branches: avoiding merge conflicts

### 1. Status goes in `status/<branch>.md`, never in `STATUS.md`

`STATUS.md` is frozen. Write your workstream's results, findings and gaps in
`status/<your-branch>.md`, and touch no other file in `status/`. Details are in
`status/README.md`. (`STATUS.md` conflicted in 10 of 11 merges because every
branch added a `Last update:` line at the top and a section at the end.)

### 2. Only edit `api/openapi.yaml`; regenerate everything else

`mgmt/api/v1/api.gen.go`, `hostd/mgmtapi/v1/client.gen.go` and
`docs/contracts/mgmt-api.md` are generated by `make api`. On a merge
conflict in any of them:

1. Resolve `api/openapi.yaml` by hand. It's the only real conflict.
2. Run `make api`. It rewrites all three files whole, conflict markers and all.
3. `git add` them. `make lint` (api-check) fails if they are stale.

Never hand-merge the generated files. The spec is embedded as plain YAML by
`api/spec.go`, not as oapi-codegen's base64 blob, so a spec change no longer
rewrites hundreds of lines of `api.gen.go`.

### 3. One item per line, and don't always append at the end

Two branches that each add an item to the same single-line list always
conflict. Two branches that each add their own line usually don't.

- **Makefile:** each target has its own `.PHONY: <target>` line right above
  it. Don't bring back the shared `.PHONY:` line.
- **Enums and lists in the spec** (for example `AuditKind`): one value per line
  in both the `description` and the `enum`.
- **Go composite literals, struct fields, `switch` cases, flag lists:** use
  one per line, as in `hostd.New`'s `&Host{...}`. When you add a field to a
  gofmt-aligned struct, give it its own comment-separated group, so a longer
  name doesn't realign (and conflict with) its neighbours.
- **Where order doesn't matter, insert in sorted or logical position**, not at
  the end of the list. The end is where every other branch is appending too.

### 4. Put new feature code in new files

The hotspots that conflicted most were `hostd/host.go`, `hostd/http.go`,
`hostd/workload.go`, `hostd/objects.go`, `netd/registry.go`,
`mgmt/service.go`, `mgmt/sqlstore.go`, `cmd/tw/main.go` and
`cmd/tw-hostd/main.go`. Put the feature's logic in its own file
(`hostd/public.go`, `mgmt/placement.go` and `mgmt/warmkeys.go` are good
examples). Keep the edit to the shared file small: one field, one route
registration, one call. Don't reformat or reorder code you aren't changing.

### 5. Don't claim an ADR number on a branch

Branches that drafted ADRs in parallel picked the same "next" number:
smart-placement drafted ADR-030, which fast-vm had already taken, and had to
renumber to ADR-033 across the code, docs and Makefile. While a decision is
Proposed on a branch, call it `ADR-<slug>` (for example
`ADR-smart-placement`). Give it the next free number only when merging to
master, and replace the slug everywhere in that same change
(`git grep ADR-<slug>`). ADRs are one file each in `docs/design/adr/`:
draft as `docs/design/adr/<slug>.md`, rename to `NNN-<slug>.md` when the
number is assigned, and add the row to `docs/design/adr/README.md` in sorted
position. `TestADRIndex` accepts a draft whose first line starts
`# ADR-<slug>`, so a design PR passes CI before it has a number.

### 6. Stay close to master

- Merge `origin/master` into your branch early and often: when you start,
  after any PR lands that touches your hotspots, and right before you open
  the PR. Ten small conflicts are easier than one big one.
- When two workstreams need the same refactor (a new store method, a shared
  type, a schema column), land it first as its own small PR, then build on it.
- After resolving conflicts, run `make lint test` before you push. A clean
  textual merge can still be semantically wrong; the 11-file fast-identity ×
  public-ingress merge was one.
- Never use bare `git stash` / `git stash pop`. The stash stack is shared with
  every other worktree. Use a WIP commit instead.

## Issue labels: who acts next

Two labels say whether an issue is waiting on the maintainer or ready for an
agent. An open issue has at most one of them.

- **`needs-decision`**: blocked on the maintainer, for a design choice, a
  product call, or an answer to a question. Agents don't start work on these
  issues.
  - Add it when you file an issue that you can't resolve without such a
    choice, for example "fix it or document it" or "which of these
    behaviours do we want". Say so in the issue body: list the options with
    their trade-offs, give your recommendation, and say what happens
    meanwhile (for example "the checker records it as a note").
  - Also add it to an existing issue when your work stops on such a
    question. Put the question in a comment.
- **`agent-ready`**: scoped and decided, so any agent can pick it up without
  asking anything. The body says what to change and how to know it's done.
  - The maintainer adds it, usually when replacing `needs-decision` with the
    answer.
  - An agent may file an issue with it directly when nothing is left to
    decide: a confirmed bug with a clear fix, or a flaky test.
  - When you start on one, comment with your branch name, so two agents
    don't take the same issue.

When you pick up an `agent-ready` issue and find a decision that isn't in it,
stop. Swap the label for `needs-decision` and comment with the question.

## Definition of done (before you open or merge a PR)

CI (`.github/workflows/ci.yml`) runs `make lint test` on every PR, and
master accepts a PR once its `ci-ok` check passes. The branch doesn't have
to be up to date with master, so when another PR lands first you don't need
to merge `origin/master` again and rerun CI, unless the two PRs touch the
same code. The CI run on each push to master is what catches two PRs that
pass alone and break master together (as #54, #55 and #57 did). If master
goes red, fixing it comes before landing anything else.

1. **Merge `origin/master`, then `make lint test`** locally (rule 6). Don't
   push to find out whether CI passes.
   **Docs-only branches** (`sh scripts/docs-only.sh` exits 0: every changed
   file is `.md`, none under `testdata/` or `e2e/`) run `make lint-docs
   test-docs` instead. CI does the same for them, so they don't need the full
   run.
2. **Run the extra suites for what you touched.** CI doesn't run these:

   | You changed | Also run |
   | --- | --- |
   | `mgmt` store or `mgmt/migrations/` | `make test-pg` |
   | anything in `mgmt` every replica runs (leases, mints, reaper, throttles, kills, audit) | `make e2e-multimgmt` (needs Docker) |
   | placement, leases, D1 across moves | `make e2e-placement` |
   | locks / leader election | `make e2e-locks` |
   | Queues | `make e2e-queues` |
   | logs, metrics, traces | `make e2e-observability` |
   | templates, `js/packages`, SDK compat | `make templates-typecheck test-sdk` |
   | wrangler config or bundling | `make e2e-wrangler` |
   | how a Cloudflare project runs unmodified: wrangler config or bundling, assets, bindings (D1, KV, R2, Queues, Workflows, Durable Objects), `nodejs_compat`, the runtime wrapper (`hostd/gen`) | `make e2e-compat` |
   | anything `make changes-check` calls upgrade-relevant | `make e2e-upgrade` |
   | `tw upgrade` on a `tw up` machine, or how `tw up` restarts | `make e2e-tw-upgrade` |
   | the launch demo: `scripts/demo*.sh`, `internal/demogrant`, the `mcp` or `agent` template's routes, `tw ls --json` or `tw status --json` fields | `make demo-test` |
   | `install.sh` / `get.sh` | `make install-test` |
   | the npm CLI packages (`js/cli/tailworks`, `scripts/npm-cli-packages.sh`, `internal/npminstall`) | `make npm-cli-test` |

   The suites that need credentials, a real tailnet, Docker, KVM or a Mac's
   virtualization (`e2e-real`, `e2e-public`, `e2e-compat`, `e2e-vm`,
   `e2e-vz`, `e2e-headscale`, …) are fine to skip if you can't run them.
   Say so in the PR.

   `.github/workflows/nightly.yml` runs the credential-free suites
   (including `e2e-headscale`) every night, and `test-pg` against a
   Postgres service container on PRs that touch `mgmt/`. That is a
   backstop, not a reason to skip the table above.
3. **Generated and registered things:**
   - API: edit `api/openapi.yaml`, run `make api`, commit the output (rule 2).
   - Release notes: when `make changes-check` asks for one, add a
     `changes/<branch>.md` fragment.
   - New CLI command: one entry in `commands` (`cmd/tw/main.go`) with its
     `group:` and `short:` (≤ 60 characters). There is nothing else to
     register.
   - Command, flag or help text change: run `make cli-docs` and commit
     `docs/cli.md` (`TestCLIReferenceUpToDate` fails when it is stale).
   - New error code: add it to `docs/errors.md` with "When" and "Fix".
   - Template or binding change: run `tw types` and commit the template's
     `worker-configuration.d.ts`.
4. **Status:** update `status/<branch>.md` (rule 1) with the commands you
   ran and their results.
5. **PR body:** what changed and why, and a **Tests** section listing the
   commands you actually ran and their results. List anything you skipped,
   and why.
