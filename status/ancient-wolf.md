# ancient-wolf: interface simplification audit (2026-11-24)

Branch `ancient-wolf` (worktree; no code changed). Independent finders audited each interface lens; every finding was then attacked by three adversarial verifiers (functionality, security-perf, simpler). The main body keeps the 77 findings from the first verification pass that survived with at most one refutation and adopts the verifiers' amendments; the Addendum adds the 21 further findings a second pass confirmed and the 46 a third pass confirmed, and lists the 14 refuted findings and the 238 knobs the finders deliberately kept. Every finding has now had three verifiers. Five high-impact items were spot-checked against the code at HEAD `ed4d2831`; corrections are marked "(spot-check)".

## Summary

The product's core is already simple: a bare `tw up` prompts for one secret and installs a login service, `tw init hello && tw deploy` is the whole app path, and nearly every security knob defaults to the safe side. The complexity the owner senses is at the edges: flags that exist for tests or scale-out topologies sit in the same alphabetical list as the four a homelab user needs (`tw up --help` is 79 lines, `tw-hostd -h` has 68 flags, `docs/cli.md` repeats `--state-dir`/`--json` 106 times); the quick start still teaches `--apply-policy` twice and `--cascade` on every `tw kill`; several auto-detectable values are asked for (KV namespace, tag `tag:tw-wl-<name>`, the join file's control/mgmt URLs); and a handful of commands exist only to feed another (`tw release`, `tw custody`, the five-command manual rollback and uninstall). Very little is actually unnecessary: 238 knobs were examined and kept because they protect isolation, audit integrity, a measured performance default or a real topology.

Top recommendations: (1) make the policy write the interactive default on a terminal while keeping `--yes` alone inert and automation on `--apply-policy --yes`, so the README collapses to three steps; (2) add one help mechanism (common / grouped / hidden flags, globals printed once, subcommand lists on bare `--help`) and regenerate `docs/cli.md`, which roughly halves it with zero behaviour change; (3) flip four defaults that every doc and test already types or works around (`tw kill` cascades, `tw ls` lists every live object and says when it truncates, bare `tw logs` shows your app, bare `tw audit` shows the newest 50); (4) derive what is derivable (`tailnet.tags`, KV namespace from the single binding, host join settings from the join file, `tw deploy`'s workload name at runtime); (5) give lifecycle verbs one command each (`tw upgrade rollback`, `tw uninstall`, `tw upgrade fleet|import`). Everything else is housekeeping: remove `--push-port` (broken by construction) and 14 zero-user daemon flags, stop shipping `tw-netd`, delete the unread `agent` key, and fix four schema/doc drifts that make documented configs fail.

## Principles

- **Sane defaults that do what every doc already types.** When every quick start, skill and test passes the same flag (`--cascade`, `--apply-policy`, `--all` for `tw audit`), the flag is the default and the opposite becomes the opt-out.
- **Progressive disclosure, never removal of parseable surface.** Flags for tests, tuning and other topologies stay accepted, stay in completion and stay in `docs/cli.md`, but `--help` prints the common set first and the rest under a heading. Nothing that an e2e suite or saved `tw.json` relies on changes meaning.
- **Derive, don't ask.** If the CLI, mgmt or the bundle already knows the value (the workload tag, the only KV binding, the control URL the host must join, the deployment's name), fill it in and print what was chosen; ask only when the answer is genuinely ambiguous.
- **Loud, explicit opt-ins for anything unsafe.** `--insecure-shared-host`, `--allow-experimental-flags`, `--allow-unsigned`, `--force-takeover`, `--yes` on destructive commands and policy writes keep their names and their fail-closed defaults; what changes is that `tw up`/`tw status` now say when a saved unsafe flag is in effect.
- **Wrangler parity where a wrangler user would reach for muscle memory** (`--env`, `--var`, `kv key put --ttl`, `secret bulk`, `d1 migrations`), tw's own verbs (`ls`, `rm`, `add`, `set`) everywhere else, and both spellings accepted silently.
- **Config over flags for rare topology, but only via mechanisms the repo already has** (`tw.json` written by `tw up`, the join file, the hostd heartbeat). No new operator-edited file without an ADR.

## Recommendations

### A. First run and `tw up`

#### A1. Prompt-to-write the policy by default on a terminal; `--yes` alone never writes

Merges `up-apply-policy-default`, `onboarding-auto-apply-policy`, `deploy-apply-policy-default`, `up-yes-semantics`.

**Current.** `tw up --apply-policy` (cmd/tw/up.go:109) and `tw deploy --apply-policy` (cmd/tw/app.go:398, gate at app.go:485-494) are opt-in; without the flag `tw up` prints the missing lines and continues (up.go:717-768) and a first `tw deploy` fails `acl_denied` whose fix text (cmd/tw/public.go:124) never mentions `--apply-policy`. README teaches the flag twice (README.md:108, 125). `--yes` on `tw up` is documented as "accepted and ignored" (up.go:108), yet `tw upgrade` restarts with `tw up --yes` (cmd/tw/upgrade.go:911) and every e2e passes it. PR #357 (one day old) made "one flag, one rule"; the simpler verifier refuted both prompt-by-default findings on that ground, so this is an owner decision to revisit, with ADR-021:10 on the owner's side ("two interactive consents: the policy diff, and creating the trust credential").

**Proposed.**
1. `tw up` (Tailscale OAuth and Headscale), `tw tenant add`, `tw deploy`, `tw policy --apply`: when stdin is a terminal, `--json` is off, lines are missing and the write is known to be possible (ValidatePolicy on the merged policy did not 403: cmd/tw/up_policyapply.go:164-176; for deploy, add `canWrite` to mgmt's dryRun result in api/openapi.yaml, then `make api`), show the diff and ask `[y/N]` exactly as `confirmBootstrapWrite`/`confirmPolicyWrite` do today. "y" writes through the unchanged additive/validated/If-Match path. "n" continues as plain `tw up` does now (print the missing lines; `policy_missing_tag_owners` hard stop stays when `tag:tw-mgmt` is unowned, cmd/tw/oauth.go:160; Headscale keeps its stop, cmd/tw/headscale.go:156); for deploy "n" falls back to today's `acl_denied` snippet.
2. Without a terminal, with `--json`, or with a bare `--yes`: unchanged, print-only. Automation keeps `--apply-policy --yes`. This leaves every `tw up ... --yes` in e2e/cliflow, e2e/headscale, upgrade.go:911 and cmd/tw/cli_test.go byte-for-byte unchanged.
3. `--apply-policy=false` is the explicit "never ask, never write" switch (same spelling as `--service=false`); `tw upgrade`'s restart passes it (upgrade.go:911) so an unattended restart is pinned to never touching the policy.
4. Deploy fallbacks: any plan failure (403 `tenant_forbidden` for team tenant admins since `ApplyWorkloadPolicy` is `x-tw-role: admin`; `policy_write_denied` for a Read-only client; Headscale file-mode) prints one line and falls through to `preflightFailure(pf)`, so the paste path is never lost. Skip auto-apply under `--allow-missing-grants`. Apply the same to `--preview` (cmd/tw/preview.go:176) or say it keeps the snippet.
5. Independently of the default (land first, no decision needed): add "or let tw add them (shows the lines and asks first): `tw deploy --apply-policy`" to the fix at public.go:124; fall back to the snippet on `policy_write_denied` at app.go:485-489; fix `--yes` help at up.go:108 to tenant.go:173's wording.
6. Docs and tests: README steps 4-5 become `tw up` / `tw deploy`; docs/INSTALL.md:261-272 and :973, docs/headscale.md:51-55, docs/errors.md (`acl_denied`, `confirmation_required`, `cancelled`), agent/skills/tw-deploy and tw-policy SKILL.md (agents run `--json`, show the snippet, pass `--yes` only after the user agreed), security/RED-TEAM.md:843 and THREAT-MODEL.md:369 ("only after an interactive y/N, or `--apply-policy --yes`"), `make cli-docs`. Tests: `tw up --yes` and `--json --yes` on a fresh state dir with a write-scoped fake perform zero `POST /acl`; implicit "y" writes exactly the bootstrap diff; tenant-admin plain `tw deploy` still yields `acl_denied`; `--apply-policy=false` never prompts.

**Why it's safe.** The write itself is unchanged: `upPolicyWant` never widens an existing tag's owners (up_policyapply.go:83-112), the merge is control-plane validated before the prompt, written with If-Match plus one retry, audited as `policy_apply` (mgmt/policyapply.go:143-145), and the caller grant rules in mgmt/callergrant.go:11-33 still apply. The gate moves from a flag to the prompt that already exists; non-interactive runs cannot write without the explicit pair. Verifier amendments adopted in full.

**Effort.** medium. **Breaking.** no (interactive-only change; a `changes/` fragment still documents the new prompt).

#### A2. First-run prompt prints the tag line, console URLs and scopes

`onboarding-first-run-prompt-guides-console`.

**Current.** `promptOAuthSecret` prints one line ("…see the README", cmd/tw/up_defaults.go:59-60) while the full guidance (steps, scopes, snippet, `consoleOAuthURL`) lives in `oauthConsoleSteps()`/`mintModeRequired()` (cmd/tw/oauth.go:27-38, 111-127) and is shown only without a terminal.

**Proposed.** Add `consoleACLURL` next to `consoleOAuthURL`; make `oauthConsoleSteps()` return three steps shared by both paths: (1) Access controls URL + `"tag:tw": ["autogroup:admin"]` "inside the existing tagOwners section; the one line tw can't write; `tw up` writes the rest after showing it, or prints what is missing"; (2) Trust credentials URL; (3) scopes with least privilege visible: Auth Keys › Write (tag:tw) required; Policy File › Write for the write, Read to paste yourself; optional Devices › Core › Write (tw kill deletes the device) and Services › Write; "scopes can't be changed on an existing client". `mintModeRequired` appends its no-terminal step and the snippet; the prompt appends the hidden-input line. No browser opening (SSH to a headless box is the common case). Add a unit test that the steps contain both URLs, the tag line, "Policy File" and the "can't be changed" clause; keep "Auth Keys", "tag:tw", "--oauth-client-file" so cmd/tw/oauth_test.go:85-93 and e2e/cliflow/cliflow.go:484 pass.

**Why it's safe.** Text only; the secret path (term.ReadPassword, prefix check, 0700/0600 save) and the `--json`/non-TTY gates are untouched. **Effort.** small. **Breaking.** no.

#### A3. Report saved unsafe flags in `tw up` and `tw status`

`guardrails-sticky-unsafe-flags-silent`.

**Current.** `keepSavedUpFlags` (cmd/tw/up_saved.go:28-35) re-applies `--insecure-shared-host`, `--allow-experimental-flags`, `--local-dev`, `--allow-sibling-egress`, `--ephemeral` from tw.json on every later `tw up` and on `tw upgrade`'s restart; nothing prints that (only `tw doctor` mentions `--insecure-shared-host`, cmd/tw/doctor.go:296-297).

**Proposed.** New file `cmd/tw/up_unsafe.go`: `! unsafe   --insecure-shared-host (tenants NOT isolated), --local-dev (dev-only transport) · saved in <state>/tw.json; clear with tw up --<flag>=false` printed by `tw up` (after the host line) and `tw status` (next to the internet line), also on the first run that sets the flag. Unsafe set: `insecure-shared-host`, `allow-experimental-flags`, `local-dev`. `--ephemeral` and `--allow-sibling-egress` go on a neutral `› saved` line (ephemeral is a documented mode used by the demo; sibling egress runs under the same checks per ADR-053:137). JSON: additive `unsafeFlags []string` on `upResult` and `statusResult` (omit in `remoteStatus`), added to `$defs/up`/`$defs/status` in schema/cli.schema.json, `changes/` fragment of kind `cli-json`. In `tw status`, cross-check `hv.InsecureSharedHost` (hostd/http.go:748) and mark a mismatch.

**Why it's safe.** Reporting only; sources are `Config` fields `tw up` already writes. **Effort.** small. **Breaking.** no.

#### A4. Remove the four dead `tw up` tuning flags; wire the three ignored ones

Merges `up-remove-dead-tuning`, `ergonomics-hide-test-only-up-flags` (removal half), `up-fast-identity-knobs-ignored`.

**Current.** `--heartbeat`, `--kill-tombstone`, `--device-delete-delay`, `--push-port` (cmd/tw/up.go:119-121, 132) have zero users outside up.go and one e2e (e2e/headscale/twup_test.go:85). `--push-port` is broken by construction: the policy snippet hardcodes `defaultPushPort` (up.go:40, 50 via policy.InfraSnippet) while hostd listens on the flag's value, so a non-default port makes mgmt's kill pushes hit a port the grant does not allow. Conversely `--warm-keys`, `--pool-nodes`, `--port-mapping` (up.go:125-127) are saved to tw.json but only the separate layout reads them (cmd/tw/state.go:549-566); `superviseSingle` hardcodes `WarmKeys: mgmtd.DefaultWarmKeys` (up.go:1119), `PoolNodes: hostdrun.DefaultPoolNodes` (up.go:1140) and never sets `PortMapping`, although docs/INSTALL.md:861-878 promises they work.

**Proposed.** Drop the four flags. Do not fall through to the daemons' defaults: define `upHeartbeat = 1s`, `upKillTombstone = 12s`, `upDeviceDeleteDelay = 8s` as constants, keep writing them into tw.json when the saved field is empty (mgmt treats delay 0 as an immediate device delete, mgmt/service.go:2547; `tw kill` prints the saved value, cmd/tw/ops.go:306), keep the `pushPort` read fallback (up.go:975-977) and stop writing it; delete the cross-flag check (up.go:145-148) and the `keep()` lines (up_saved.go:37-39, 46-48); update cmd/tw/up_saved_test.go:34-39,67; drop the two flags from e2e/headscale/twup_test.go:85 (the 60 s poll absorbs the default delay). For fast identity: new `cmd/tw/up_identity.go` with `(c Config) identitySingle(mo *mgmtd.Options, ho *hostdrun.Options)` (nil = defaults, explicit 0 = off, `PortMapping` passthrough), two one-line calls in `superviseSingle`, and `netd.DisablePortMapping()` before `mgmtd.Start` when `!s.Cfg.PortMapping` (mgmt's node is created before hostdrun's call today, against netd/registry.go:1023's "before any tsnet node exists"). Use `mgmtd.DefaultWarmKeys`/`hostdrun.DefaultPoolNodes` as the flag defaults so they cannot drift. No Headscale auto-default for `--pool-nodes 0`: ADR-015:13 records that the node-side rename works there. `changes/` fragment: saved `--warm-keys 0`/`--pool-nodes 0`/`--port-mapping` in the default layout now take effect. Run `make cli-docs`, `make e2e-tw-upgrade`.

**Why it's safe.** Removing a flag nobody passes and fixing silently ignored ones; `RevokeWarmKeysOnClose: true` (up.go:1119; THREAT-MODEL H25) is untouched. **Effort.** small. **Breaking.** yes for the four flags (no known user; `tw.json` fields are kept and read, so existing installs restart unchanged).

#### B3. Data commands register flags per verb; one subcommand scanner

Merges `data-help-flags-per-sub`, `data-subcommand-scanner`.

## Considered and rejected

- **Remove `tw tenant set --pool`**: refuted; hosts can be placed in a pool today via the admin API (`POST/PUT /v1/hosts` `pool`, mgmt/service_v1.go:375), and the pool is a documented tenant-isolation control, so removing the only CLI lever weakens isolation and strands existing config.
- **Gate test-only daemon flags on `-local-dev`**: refuted; `tw up --separate-host` passes `-tsapi-url` without `-local-dev` (cmd/tw/up.go:935-943), `-local-dev` on tw-mgmt is a privileged unix-socket admin mode rather than a test marker, and a real-tailnet suite would break. (Its usage-section half is adopted in F2.)
- **Replace the ai-agent template's `MCP_URL` var with a wrangler service binding**: refuted; `TestVercelAI` (`make test-sdk`) depends on `MCP_URL` naming a deployed workload, and deriving `connects` from `services` adds a second source of truth without removing the preflight.
- **Take `tw backup`'s full hostd copy in `tw upgrade` so rollback can restore DO storage**: refuted 3/3; ADR-041 §4's two-step format rule (reader ships one release before the writer) means a one-step rollback never meets a newer hostd/netd format, and copying DO storage and R2 bytes on every upgrade can be many GB on a homelab disk. Smaller accepted alternatives: gate the plan on the catalog's `formats` the way the `contracted` guard does (cmd/tw/upgrade.go:509-517), or an opt-in `tw upgrade --hostd` for SQLite stores only.
- **Let `tw upgrade` drive `npm install -g`**: refuted 2/3; it bypasses the pinned-key signature path the threat model names for `tw upgrade` (security/THREAT-MODEL.md:128-135) and the staged plan/version gate. Accepted half: one `installChannel()` classifier (tarball prefix | npm | npx | checkout | other) shared by `tw doctor`, `tw version --check` and `tw upgrade --plan`, so all three print the same one command.
- **Split docs/containers.md into a 180-line guide and a design appendix**: refuted 2/3; the "internals" half holds the only prose on `tw host vmcheck --container`, the isolation guarantees security-model.md points at, and the per-tenant image cache, and `tw docs` must keep them offline. - **Fold the three deployment list routes and schemas into ListDeployments filters**: refuted in the third pass; folding the three deployment list routes is breaking under ADR-041's additive-only `/v1`, and `tw deployments` / `tw previews --json` are stable cli-json contracts.

- **tw-mgmt's four -local-dev knobs always travel together; rotate the host token by default and derive the paths**: refuted in the third pass; rotate-by-default breaks replicas that share one token file (e2e/multimgmt), and the typical user never sees these flags.
