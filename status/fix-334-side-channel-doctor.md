# fix-334-side-channel-doctor: side-channel posture in `tw doctor` and the docs

## What

- Issue #334 (Workers threat-model review): tailworks separates tenants
  with a process or a VM per workload, so the host kernel's and CPU's
  side-channel mitigations are the whole defence between tenants (and
  between tenant code and tw-hostd / tw-netd / tw-mgmt on the same cores),
  and nothing checked or documented them. "No native code" doesn't hold on
  the Node tier or in a microVM guest.
- New `tw doctor` check **`side_channels`** (group Isolation):
  - `cmd/tw/doctor_sidechannel.go` (portable): `readSideChannels(root)`
    reads `<root>/sys/devices/system/cpu/vulnerabilities/*` (any entry
    starting with `Vulnerable`), `<root>/sys/devices/system/cpu/smt/active`,
    `<root>/proc/cmdline` (`mitigations=off`, `nosmt`) and
    `<root>/sys/kernel/mm/ksm/run`; `report()` turns it into ok or warn,
    never fail. The detail always ends with when it matters (more than one
    tenant, a Node-tier workload, the microVM tier) and points at
    docs/security-model.md "Side channels".
  - `cmd/tw/doctor_sidechannel_linux.go`: runs it on `/`; while tailworks
    runs, appends what this host serves now (tenants, Node-tier workloads,
    the microVM tier) from hostd's status.
  - `cmd/tw/doctor_sidechannel_other.go`: macOS and others skip with "the
    posture can't be read … a macOS host is development-grade for tenants
    that don't trust each other".
  - Wiring: one `run(...)` line in `cmd/tw/doctor.go`, one row in
    `doctorMetas` (`cmd/tw/doctor_render.go`), the doctor help text in
    `cmd/tw/main.go` (docs/cli.md regenerated).
- Docs:
  - docs/security-model.md, new "Side channels" under "When a host is
    shared between tenants": what tailworks relies on, what the operator
    keeps on (mitigations on, SMT off or accepted, KSM off), that the Node
    tier and microVM guests run native code, that a macOS host is
    development-grade, and the **Decision** not to gate.
  - docs/INSTALL.md: the microVM tier's "What you need" links Firecracker's
    production host setup guide and names SMT, KSM and mitigations; the
    Linux `tw doctor` table has a `side_channels` row.
  - security/THREAT-MODEL.md §3: the side-channel residual per tier
    (process/workerd, process/Node, microVM Linux, macOS).
  - security/LEDGER.md: hypotheses row `H-host-sidechannel` (Medium,
    disclosed, `cmd/tw.TestDoctorSideChannelsFixtures`, #334) and a run-log
    line.
- `changes/fix-334-side-channel-doctor.md` (kind security, no upgrade
  kinds; `make changes-check` didn't require one, it is there for the
  release notes).

## Decision: no gate (issue option 3)

hostd does not refuse a second tenant on a host whose kernel reports
`Vulnerable` or `mitigations=off`. Reasons, also recorded in
docs/security-model.md: single-tenant dev hosts are the common case and a
gate gains them nothing; the kernel's `Vulnerable` strings vary by CPU and
kernel (the test guest's `Vulnerable: Safe RET, no microcode` is a partial
mitigation), so a gate would need per-entry judgement; and an operator
override would be needed anyway (as `--insecure-shared-host` is today).

Possible future gate, if wanted: treat `mitigations=off` (unambiguous,
operator-chosen) as `sandbox_unavailable` does, with
`--insecure-shared-host` as the override, and leave `Vulnerable` entries
and SMT as warnings. Not in the code; this file is where it is tracked.
