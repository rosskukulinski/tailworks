Last update: 2026-11-23 21:40 PT. #302: request.cf geo fields documented as absent, regression-tested.

## What changed

- `request.cf` carries no geolocation on tailworks (tailnet `100.x` callers
  have no IP location; public/Funnel requests are not GeoIP'd). Documented in
  `docs/COMPAT.md` (`fetch` row; public-routes table), a new
  `docs/wrangler.md#requestcf` section, and `docs/public-ingress.md`.
- The keys tailworks does set, checked by grepping where the cf blob is
  built (`netd/ingress.go` `CFBlob`, `netd/public_serve.go`,
  `hostd/http.go` `ingressHandler`) and confirmed by the test's log:
  `objectId`, `tailscale` (`caller` + `seal`, or `requester` for public),
  `traceId`, `tw`. Nothing sets any geo key, and workerd adds none.
- Regression test: the `pubprobe` fixture reports `cfKeys` and `cfGeo`
  (which of Cloudflare's geo keys are present at all); `TestPublicIngress`
  asserts `cfGeo` is empty for a public and a tailnet request
  (`hostd/cfgeo_test.go`). Checked that it fails when hostd sets
  `blob["colo"] = ""`.

## Tests

- `go test ./hostd -run 'TestPublicIngress$' -v`: PASS; logs
  `request.cf keys [objectId tailscale traceId tw]` for both paths. With a
  temporary `colo: ""` injected in hostd: FAIL as expected (reverted).
- `make lint`: ok (before and after merging origin/master).
- `make test` (offloaded to mbp with `mbp-test.sh test`, after merging
  origin/master): ok, no failures.
- `make changes-check`: ok (no upgrade-relevant paths), so no changes fragment.

## Not done / follow-ups (open questions in #302)

- GeoIP for public (Funnel) requests: would need a bundled database
  (licensing, size) or an opt-in operator hook. Not done.
- Static per-host location (operator-set `colo`/`country`/lat-long per
  host): not added. It would describe the host, not the caller, so it
  would mislead code like the globe template that wants the client's
  position.
