Last update: 2026-11-23 21:40 PT. Tenant code no longer sees netd's x-tw-object routing header (#303).

# fix-303: strip internal x-tw-* routing headers before tenant code

## What

- netd stamps `x-tw-object` (`netd.HeaderObject`) on ingress so hostd can
  find the object. hostd's `ingressHandler` (`hostd/http.go`) read it and
  then passed it on to workerd, so a Worker's `fetch`, a Durable Object and
  a Workflow all saw it in `request.headers`.
- hostd now calls `stripRoutingHeaders` (new file `hostd/routingheaders.go`)
  right after it reads the object ID. That drops every `x-tw-*` / `tw-*`
  request header except `x-tw-cf`, which is workerd's `cfBlobHeader`: workerd
  consumes it itself and exposes it as `request.cf`. netd already strips the
  client-sent copies, so whatever is left with those prefixes is ours.
- `ingressHandler` is the only path from netd into workerd (every tier and
  public ingress go through it). Queue, cron, approval and intercept
  deliveries go from hostd straight to workerd and only set `x-tw-cf`.
  Nothing downstream of hostd read `x-tw-object`.
- Standalone netd (`tw-netd -upstream`, `netd/testdata/workerd/platform.js`)
  still passes `x-tw-object` to its own platform worker, which uses it for
  routing. That is netd's upstream contract and doesn't change.
