# R2 buckets

tailworks runs Cloudflare's R2 binding: declare `r2_buckets` in `wrangler.jsonc`
and use `env.BUCKET.get/put/head/delete/list` and multipart uploads as on
Cloudflare. Your code gets workerd's own R2 binding, so `R2Object`,
`R2ObjectBody` (`.body`, `.text()`, `.json()`, `.arrayBuffer()`),
`writeHttpMetadata()`, `onlyIf` and ranged reads behave as they do there.
What's supported, measured, is in [COMPAT.md](COMPAT.md#r2). The design is
[ADR-036](design/adr/036-r2-buckets.md).

```jsonc
// wrangler.jsonc
{
  "name": "photos",
  "main": "src/index.js",
  "compatibility_date": "2026-04-01",
  "r2_buckets": [{ "binding": "BUCKET", "bucket_name": "photos" }]
}
```

```js
export default {
  async fetch(req, env) {
    const key = new URL(req.url).pathname.slice(1);
    if (req.method === "PUT") {
      // req.body streams into the bucket; it isn't buffered anywhere.
      const o = await env.BUCKET.put(key, req.body, {
        httpMetadata: req.headers,
        onlyIf: { etagDoesNotMatch: "*" }, // only if the key is new
      });
      return o ? Response.json({ etag: o.etag }) : new Response("exists", { status: 412 });
    }
    const o = await env.BUCKET.get(key, { range: req.headers, onlyIf: req.headers });
    if (!o) return new Response("not found", { status: 404 });
    const h = new Headers();
    o.writeHttpMetadata(h);
    h.set("etag", o.httpEtag);
    return new Response("body" in o ? o.body : null, { status: "body" in o ? 200 : 304, headers: h });
  },
};
```

A bucket appears on its first write. It belongs to the workload: two
workloads that both name `photos` have two different buckets.
`preview_bucket_name` and `jurisdiction` are accepted and ignored.

## Where the data lives

- **The index** (every key with its size, etag, upload time, metadata and
  where its bytes are) is a platform store. It is journaled to tw-mgmt
  before a write is acknowledged, sealed at rest, and fenced to the host
  that holds the workload's lease, like a [secret](secrets.md). It
  survives a redeploy, a crash and a move to another host.
- **The bytes** are blobs in the host's **R2 backend**, which the operator
  of each host sets with `tw-hostd` flags. Only tw-hostd talks to it;
  the workload never sees its address or credentials.

| `-r2-backend` | Bytes in | Use for |
|---|---|---|
| `fs` (default) | `<data-dir>/r2` on the host (`-r2-dir` to move it) | `tw up` on one machine, `tw dev` |
| `s3` | a bucket of any S3-compatible service: MinIO, Garage, SeaweedFS, AWS S3, Cloudflare R2 | more than one host |

`tw dev` uses `fs` in its temporary directory, with the index in its
in-memory control plane: buckets last one `tw dev` run.

With `fs`, a workload that moves to another host keeps its index but not
its bytes: getting an old object there fails (`r2_blob_missing`). With
`s3`, every host that can run the workload must use the same backend.

```sh
# on each host (credentials from the environment, or a KEY=value file)
export TW_R2_S3_ACCESS_KEY_ID=… TW_R2_S3_SECRET_ACCESS_KEY=…
tw-hostd … -r2-backend s3 -r2-s3-endpoint http://minio.lan:9000 -r2-s3-bucket tw \
  [-r2-s3-region us-east-1] [-r2-s3-prefix tw/] [-r2-s3-virtual-host] [-r2-s3-credentials-file /etc/tailworks/r2.env]
```

The backend bucket holds every tailworks bucket of every tenant on these hosts,
one prefix each: `<prefix>t/<tenant>/w/<workload>/b/<bucket>/<blob-id>`.
tw-hostd builds that name itself from the workload making the call, so no
workload can reach another one's objects. Object keys never become paths.
Tailworks encrypts nothing itself with the `fs` backend (use disk encryption);
with `s3`, encryption at rest is the service's.

## How it's tested under faults

The data-plane chaos loop checks these guarantees with real hosts and a
real tw-mgmt (`make e2e-dataplane-r2`, every night;
[e2e/dataplane/ledger/r2.md](../e2e/dataplane/ledger/r2.md)). Clients
put, get, head, delete, list and upload in parts on a few keys, against
one copy of a workload (`fs` and `s3` backends) and against two replicas
(`s3`, a Garage container). Meanwhile hosts are killed (also in the middle of
a large put), crashed, stalled and moved, cut off from tw-mgmt or from
the S3 service, and tw-mgmt restarts. The checks:

- **R1**: each key behaves as one register for put, get and delete,
  across replicas, while tw-mgmt is reachable.
- **R2**: an acknowledged put survives crashes and moves with its bytes
  (`s3`), or fails with exactly `r2_blob_missing` after a move (`fs`),
  and the index still has it. Bytes and etags always match, and a put
  with a wrong MD5 is never stored.
- **R3**: no write is acknowledged while tw-mgmt is unreachable, or by a
  host the workload has moved away from.
- **R4**: stale reads only from a host cut off from tw-mgmt, and with a
  Durable Object class only for the first 30 s.
- **R5**: `list` agrees with the index once things settle. Blobs that no
  index row names (left by a crash) are counted.
- **R6**: a completed multipart upload is seen whole or not at all, and
  an unfinished upload is kept until it's aborted.

## From the CLI

```sh
cd my-app                         # the workload is the app's name, as for tw deploy
tw r2 bucket ls                  # the workload's buckets
tw r2 bucket create photos       # optional: a bucket appears on its first write
tw r2 object ls photos --prefix cats/
tw r2 bucket rm photos           # deletes the index now; the workload deletes the bytes on its next use
```

A `<bucket>` is the bucket's name or its binding in the app's
`wrangler.jsonc` (`tw r2 bucket rm PHOTOS` asks you to type the bucket it
resolved to); a bucket the app declares by that name wins over a binding of
the same name. `list` and `delete`, wrangler's spellings, work as well as
`ls` and `rm`. `--workload <name>` works from anywhere; `--json` prints JSON.
`tw r2 object ls` lists the bucket's index through mgmt
([`GET …/stores/r2/{name}/objects`](contracts/mgmt-api.md#operator-api)),
so it needs a tw-mgmt of the same release or newer. Reading or
writing object bodies from the CLI (`tw r2 object get|put`) isn't built:
the bytes are in the hosts' backend, which mgmt can't reach.

## Limits and differences

- R2's limits: keys up to 1 KiB, custom metadata up to 8 KiB, objects up to
  5 GiB − 5 MiB, `list` pages of up to 1000 keys (100 with `include`),
  multipart parts of at least 5 MiB but the last, up to 10,000 parts.
- One hash per put (`md5`, `sha1`, `sha256`, `sha384` or `sha512`), checked
  against what was stored; the etag is the MD5 (`<md5 of md5s>-<parts>` for
  multipart).
- Each write costs one round trip to tw-mgmt, and reads check the journal
  first, so a bucket is read-after-write consistent across a workload's
  replicas. If tw-mgmt is unreachable, writes fail. Reads answer from
  the host's copy of the index after waiting at most 2 s for tw-mgmt
  (later ones don't wait until it is back). If the workload has a Durable
  Object class (not `"fence": "never"`), the host stops the whole workload
  after 30 s without tw-mgmt, reads included. With the `s3` backend and
  replicas, a read from such a stale copy can also fail with
  `r2_blob_missing`, when another replica has since replaced or deleted
  the object and its old bytes are gone.
- Not supported: public buckets and custom domains, presigned URLs and the
  S3 API to a bucket, lifecycle rules (unfinished multipart uploads are
  kept until aborted), event notifications, storage classes
  (`storageClass` is `Standard`), `ssecKey`, sharing a bucket between
  workloads, bucket mounts in [containers](containers.md).
